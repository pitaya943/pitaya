# Review of 0.1.4: the findings in full

The text of the 36 findings from the review of pitaya at tag `v0.1.4` (commit `e8904db`), as the reviewer wrote them. `docs/trials/w8.md` ("Review of 0.1.4") has the one-line list, how each sorts under the threat model (D59), and its current status; this file is what a builder fixes against and what a verifier's brief quotes.

The text is not updated as findings are fixed: it describes 0.1.4. Severity is the review's own, set before D59. "Where" gives paths under `plugin/` (or `plugin/docs/guardrails/`) with 0.1.4's line numbers. F01 to F32 were first found at 0.1.2 and re-checked at 0.1.4; N01 to N04 were new in 0.1.4.

Evidence: "reproduced" means the reviewer ran it with real inputs; "code read" means it follows from the code and docs; "partly unverified" means part of it depends on GitHub's or the client's behaviour and wasn't reproduced live.

## N01: The tree-equality proof ignores history: `merge -s ours` makes an Owner's change silently revert later

- Severity: High. Category: CI gates. Evidence: reproduced.
- Where: check_verdict.py:79-82,141-163; files/scope/scope.yml:97-110 (same block in 6 other workflows); docs/decisions.md D58
- Problem: Both the sync PR and the PASS carry-over prove only that the head's tree equals the tree of the base merged with some commit. `git merge -s ours <commit>` leaves the tree alone and records that commit as merged. Tested: a sync branch with one extra `merge -s ours Q` (Q being a commit on an Owner PR not merged yet, such as one tightening a ticket's scope or changing a rule file) passes the ticket checks and `verdict` (at Level 3, with no verifier). The Owner later merges Q into `main` with a merge commit; the next honest sync doesn't bring Q's content into the milestone (git considers it merged) and still passes; after the milestone PR merges, Q's change is gone from `main`. The same ours-merge on a ticket branch after a PASS also counts as "only the base merged in".
- Worst case: A correction the Owner approved and merged (a rule, a ticket's scope, a security fix) is reverted at the milestone sign-off, inside a large PR whose ticket checks are all skipped. Preconditions: Q reaches `main` by a merge commit or fast-forward (a squash is unaffected), and the agent can fetch that commit. To recover, apply Q to `main` again.
- Suggested fix: Prove the history's shape as well as the tree: every commit in `git rev-list <head> ^<base> ^<default or PASS head>` must be a two-parent merge whose first parent is on this chain and whose second is reachable from the base (carry-over) or the default branch (sync); for a sync PR, the first parent must also be reachable from the milestone branch. Add tests 3 and 4 to `tests/`.

## N02: Sync PRs are failed by the two checks that don't use "Find the ticket"

- Severity: Medium. Category: CI gates. Evidence: code read.
- Where: files/commit-author/commit-author.yml:46-60; files/progress-file/progress-file.yml:41-52; skills/plan/milestones.md:24-27
- Problem: The sync exception was added only to the shared "Find the ticket" step and to `check_verdict.py`. `commit-author` checks every commit's author on a PR the machine account opened, and a sync PR's commits include the Owner's merge commits on `main` and other people's commits; `--also-allow` is empty by default. `progress-file` treats an agent's sync PR as "changed beyond passes" whenever the Owner edited `features.json` on `main`.
- Worst case: In a project that requires these two checks on `milestone/*`, autopilot's sync PR can never merge, and F05's deadlock returns in another form; in practice the Owner reaches for the bypass.
- Suggested fix: Add the same sync test to both workflows (once N01 is fixed), or have `commit-author` skip commits reachable from the default branch.

## N03: A carried PASS means the verifier never saw the combined result

- Severity: Low. Category: CI gates. Evidence: reproduced.
- Where: check_verdict.py:150-163; guardrails/agent-merge.md:27; docs/decisions.md D58
- Problem: This is the trade-off D58 states: a PASS carries over "Update branch", and the combination is guarded only by `tests` and the ticket checks. Testing showed one reasonable side effect: a bad commit pushed after a PASS and then reverted brings the tree back to the PASS state, and the PASS carries.
- Worst case: When two tickets that each passed conflict in meaning, no verifier checks the combined behaviour; the checks only a verifier makes (mutation, error paths) aren't re-run.
- Suggested fix: Keep the design, but make "Require branches to be up to date" a prerequisite of agent-merge in the recipe rather than an option, and don't carry a PASS for a `Risk: high` ticket.

## N04: The `sync/` branch class didn't reach the other docs or the grant list

- Severity: Low. Category: Skill logic contradictions. Evidence: code read.
- Where: templates/AGENTS.md:16; concepts/states.md; concepts/layout.md:43-50; guardrails/README.md:52-67; skills/help/SKILL.md
- Problem: 0.1.4 mentions sync PRs only in `milestones.md`, `tick.md` and the agent-merge recipe. The branch grant in `AGENTS.md`, the branch table in `layout.md`, `states.md`, the guardrails README's "How the checks find the ticket" and `/help` don't know `sync/`.
- Worst case: In a cloud session, autopilot has no grant to rely on when it creates a sync branch; `/help` reports a sync PR as a branch it can't classify. `states.md` is named as the authority, yet doesn't know this kind of PR.
- Suggested fix: Add `sync/<slug>` in those five places, and add a test under `tests/plugin/` that every branch prefix the workflows recognise appears in `AGENTS.md` and `layout.md`.

## F01: The builder can issue its own verdict

- Severity: Critical. Category: CI gates. Evidence: code read.
- Where: files/agent-merge/agent-merge.yml:41; check_verdict.py:85-100; docs/levels.md:104; guardrails/agent-merge.md:23; skills/autopilot/tick.md:22
- Problem: `VERIFIERS` falls back to `MACHINE_ACCOUNT`, and the builder, the verifier and autopilot all post as that one account. `check_verdict.py` looks only at the commenter's login and the comment's shape, so a builder session that posts `## Verification: PASS` with a `Head commit:` line turns `verdict` green by itself. The docs also disagree: `levels.md` says agent-merge needs a verifier account the builder can't post as; the recipe and the skills say to use one account.
- Worst case: Level 3's only mechanical gate is void: unverified code is merged into `milestone/M<n>` by the agent that wrote it, and later reaches the Owner inside a milestone PR whose ticket checks are all skipped.
- Suggested fix: Give the verifier its own identity: make `VERIFIER_ACCOUNTS` mandatory, fail closed when a verdict's author equals the PR author or any commit author, and keep the verifier token out of builder environments. Stronger: produce the verdict from a base-context workflow (the verifier runs as an Action with a secret builders never hold). Fix the contradiction between `levels.md` and the recipe.

## F02: A FAIL is not final: editing or deleting the comment erases it

- Severity: High. Category: CI gates. Evidence: code read.
- Where: check_verdict.py:92-93,157; agent-merge.yml:18-19; concepts/states.md:48
- Problem: "Edited comments don't count" applies to FAIL as well as PASS. The verifier account (by default the builder's own account) edits one character of a FAIL comment, or deletes it, and that FAIL no longer counts; the workflow even re-runs on `edited` and `deleted` and resets the status.
- Worst case: A head that failed can be merged after one more PASS comment, and the fix-round count (the number of FAIL comments), which triggers escalation to the Owner, is wiped too.
- Suggested fix: Make FAIL one-way: an edited verifier comment that contains FAIL still counts (or any edited verdict is a FAIL); before writing the status, read the head's existing `verdict` and never downgrade a FAIL; keep the record in reviews (they can't be deleted, only dismissed) or a ledger the workflow writes.

## F03: The workflow definitions are PR-controlled; only the .py is loaded from the base

- Severity: High. Category: CI gates. Evidence: partly unverified.
- Where: files/*/*.yml ("Load the checks from the base branch"); agent-merge.yml:8-10,16-17; guardrails/machine-account.md:17
- Problem: Every ticket check runs on `pull_request`, for which GitHub uses the workflow YAML from the PR's merge commit; only the Python script is read from the base. A PR can change `scope.yml`'s steps to `echo ok`, or add a workflow whose job is also named `scope`. `agent-merge.yml` says it runs in the base context, but its `pull_request_review` trigger also runs the PR's copy of the file, with `statuses: write`, so it can set `verdict` to success directly. `read-only-paths` is the same kind of workflow and can be changed in the same PR. The only mitigation today is one sentence in the machine-account recipe: a token without the Workflows permission.
- Worst case: Whenever the agent's credential can write workflow files (the Owner's own token, a classic PAT, a GitHub App, a cloud session's integration), one PR can pass every required check of Levels 2 and 3 on its own say-so. Not reproduced on a live repository; it follows from the documented event semantics of GitHub Actions.
- Suggested fix: Move the checks that run no PR code (scope, read-only, append-only, evidence, commit-author, serial, progress, verdict) to `pull_request_target` with a base-only checkout; drop the `pull_request_review` trigger (use `pull_request_target` plus `issue_comment`). Add a base-context check that fails any PR touching `.github/**`. Where the plan allows, use the ruleset's required workflows or a push ruleset's file-path restriction. `/setup` should check and report whether the token can write workflows.

## F04: Level 4 deadlocks: a plan PR can never get a verdict, and state is read from the wrong branch

- Severity: High. Category: Branch & merge control. Evidence: code read.
- Where: skills/autopilot/SKILL.md:15,46; tick.md:9; check_verdict.py:120-122; guardrails/deep-verification.md:22; protect-main.md:41
- Problem: Level 4 tells the Chief to merge the plan PR into `milestone/M<n+1>` "once its checks pass", but that branch's ruleset requires `verdict`, and `check_verdict.py` always fails a branch that starts with `plan/`. Autopilot also looks for the `Status: active` milestone and its tickets under `docs/milestones/` on `main`; at Level 4 the cut exists only on the milestone branch, so `main` shows `planned` and an empty Tickets section, and autopilot stops in "Before the first tick".
- Worst case: Level 4 can't run as written. The likely outcome is that an agent or the Owner turns `verdict` off or uses the bypass to get moving, which removes Level 3's protection as well.
- Suggested fix: Decide and encode it in one place: either (a) a plan PR into a milestone branch gets its own check (for example a second-model review of the design and tickets) and `check_verdict.py` accepts it when the base is `milestone/*`, or (b) the Owner still merges the cut at Level 4. Change autopilot and `tick.md` to read state from the milestone branch, falling back to `main` only when it doesn't exist.

## F05: Syncing main into a milestone: what remains

- Severity: Low. Category: Branch & merge control. Evidence: partly unverified.
- Where: skills/plan/milestones.md:22-29; skills/autopilot/SKILL.md:24; guardrails/protect-main.md:36-43
- Problem: The sync PR resolves the conflict between a direct push and the ruleset. The recipe still doesn't say whether a ruleset with required status checks blocks creating `milestone/M<n>` and `sync/…` branches (untested), and `/setup`'s proof step doesn't create one for real.
- Worst case: At the start of the first milestone the agent can't create the branch and stops; the only message is GitHub's rule violation.
- Suggested fix: State the setting that branch creation needs in the protect-main recipe, and add "create a test milestone branch" to its "How to prove it works".

## F06: Below Level 3, "the Owner merges tickets" is not enforced

- Severity: High. Category: Branch & merge control. Evidence: code read.
- Where: guardrails/protect-main.md:40; skills/plan/milestones.md:27; concepts/autonomy.md:16; concepts/layout.md:49
- Problem: D56 gives every level a milestone branch, and the recommended `protect-milestones` ruleset always has Required approvals: 0. `autonomy.md` says the approval drops to 0 only together with `verdict` (D37). Levels 1 and 2 have no `verdict`, so the machine account needs only a green `tests` to merge a ticket PR into the milestone branch; the only thing in the way is `ask_on_merge.py`, which can be bypassed and which only Claude Code runs.
- Worst case: Levels 1 and 2 promise that a person merges every PR, yet an agent can merge any PR into the milestone branch, and with F07 skip the ticket checks too. The Owner sees it only as part of one large milestone diff.
- Suggested fix: Split the protect-main recipe by level: below Level 3, `milestone/*` requires one approval; it drops to 0 only in the same step that adds `verdict`. Have `/setup` and `/help` read the ruleset API and compare it with the level in the harness file.

## F07: A branch-name prefix alone skips every ticket check

- Severity: High. Category: CI gates. Evidence: code read.
- Where: files/scope/scope.yml:92-96,111-121 (same block in 6 other workflows); guardrails/README.md:63
- Problem: A head branch that starts with `milestone/` gets `skip=true`, whoever opened it, whatever its base, and whether or not it is the protected milestone branch. One that starts with `plan/` may change any existing `docs/tickets/*.md`, including another ticket's Scope, Test IDs and Test renames. Milestone PRs are skipped because "their tickets passed the checks on the way in", but nothing verifies that.
- Worst case: An agent that names its branch `milestone/x` avoids scope, read-only-paths, no-weakened-tests, done-when and evidence. At Level 2 (see F06) it can merge straight into the milestone branch; at Level 3 only `verdict` stops it (and see F01 for `verdict`).
- Suggested fix: Skip only when all hold: the base is the default branch, the head is the active milestone's branch, and a ruleset protects it. Limit plan PRs to base `main`, and forbid changing a ticket file that isn't `open` or has a PR in progress. Run an aggregate check on the milestone PR (its whole diff against the union of the merged tickets' scopes).

## F08: Comments are treated as the Owner's authority without checking who wrote them

- Severity: High. Category: Identity & trust boundary. Evidence: code read.
- Where: skills/autopilot/SKILL.md:16,38; tick.md:15; concepts/escalation.md:25; skills/ask-owner/SKILL.md:36-40
- Problem: A "stop" on the tracking issue, an answer on a `needs-owner` issue and the authorisation of an extra fix round all count as the Owner's instruction, yet no skill tells the agent to compare the commenter's login with the Owner named in the harness file. On a public repository anyone can comment; on a private one, any collaborator, a third-party bot, or the machine account itself. Issue bodies, PR comments and review-bot output are also prompt-injection entry points.
- Worst case: An outsider answers an escalation; the agent builds what they "decided" and records it in `docs/decisions.md` as the Owner's decision. Or they authorise unlimited fix rounds, or halt autopilot with one "stop".
- Suggested fix: State in `ask-owner`, `autopilot` and `build` that only a comment whose `author.login` is the Owner (with `author_association` OWNER) is an instruction; everything else is data. Sturdier: a base-context workflow adds an `owner-answered` label when the Owner replies, and agents trust only the label.

## F09: The default allow rules permit writing files, reading secrets and running commands without a prompt

- Severity: High. Category: Session hooks & permissions. Evidence: reproduced.
- Where: templates/.claude/settings.json:3-9
- Problem: `Bash(git diff *)`, `git show *` and `git log *` accept `--output=<path>`, which overwrites any file; in a test, `git diff --output=.claude/hooks/no_push_main.py` corrupted the hook, which then failed open with exit 1. `git diff --no-index /dev/null .env` prints a file the Read tool is denied (tested). `Bash(git fetch *)` accepts `--upload-pack=<command>`, which ran an arbitrary command (tested). All three match the allow patterns, and the rule-file hook stays quiet. Whether the client applies further built-in checks was not verified.
- Worst case: One prompt injection (a hostile issue body, say) can disable the hooks, read `.env` or run any program with nobody asked; this is the default Level 1 install.
- Suggested fix: Remove `git fetch *`; narrow the others to forms without dangerous flags and add deny rules: `Bash(git * --output*)`, `Bash(git *--no-index*)`, `Bash(git fetch *--upload-pack*)`, `Bash(git * --ext-diff*)`. Add these three payloads to `tests/` as regression tests.

## F10: The hooks are bypassed by simple shell indirection and by MCP tools, and the agent can rewrite what they consult

- Severity: High. Category: Session hooks & permissions. Evidence: reproduced.
- Where: templates/.claude/hooks/*.py; settings.json:25-45; ask_on_merge.py:113-125; ask_on_rule_files.py:88-95
- Problem: Let through in tests: a variable (`B=main; git push origin HEAD:$B`), a git alias, `xargs`, `$(…)`, `gh api …/merges`, `gh api …/git/refs/heads/main`, `curl` to the merge API, `gh alias`. Writes to rule files: `bash -lc '…'`, `sudo tee`, `env … sed -i`, `perl -pi`, `git checkout <branch> -- <file>`, `git apply`, `dd of=`, `cd` then a redirect, a script file. No matcher covers `mcp__*__push_files`, `create_or_update_file`, `delete_file` or `create_branch`, though the docs send cloud sessions to the GitHub tools. `ask_on_merge.py` reads `harness.md` from the working tree, so an agent that changes the Autonomy line on its own branch is no longer asked; the test is `startswith("agents merge")`, which also lets "Agents merge nothing" through (tested). The four hooks' parsers are copies that have already drifted.
- Worst case: The docs do say the hooks are not the guarantee and the ruleset is. But at Level 1 without a machine account (F11), and on milestone branches at Levels 1 and 2 (F06), the hook is the only gate.
- Suggested fix: Add matchers for the MCP write tools and check their branch and path; read Autonomy with `git show origin/<default>:docs/agents/harness.md` and compare it with an enumerated set; make the push and merge hooks return `ask` for a command they can't resolve (a `$`, a backtick, an unknown alias) and exit 2 on error (fail closed); move the parser into one module.

## F11: At the default Level 1 (no machine account), the agent is the Owner

- Severity: High. Category: Identity & trust boundary. Evidence: code read.
- Where: skills/setup/SKILL.md:28,51; guardrails/protect-main.md:21,25,38; files/*/*.yml (is_agent)
- Problem: `/setup` accepts "None" for the machine account, and the agent then acts with the Owner's credentials. The premise "an author can't approve its own PR, so only the Owner merges" no longer holds: the ruleset's bypass list is the Owner, `gh pr merge --admin` merges directly, and a bypass also skips the required `tests`. In CI, `is_agent` goes by the PR's author, so a PR opened from the Owner's account counts as a person's and skips the ticket checks.
- Worst case: What D37 calls "enforced, not just written" comes down to the hooks (F10) in the most common solo setup; one bypass merges unreviewed, untested changes into `main`. To roll back, `git revert` the merge commit (never a force push).
- Suggested fix: Make a machine account (or a restricted fine-grained token or GitHub App) part of Level 1. If the user insists on None, `/setup` should say in the harness file and its output that merge protection is then the hooks alone. Give the Owner's own PRs another route (CODEOWNERS with a second reviewer, for example) instead of a routine bypass.

## F12: The commit-author check is spoofable with the account's noreply email

- Severity: Medium. Category: CI gates. Evidence: code read.
- Where: files/commit-author/check_commit_author.py:10-12,45-51; guardrails/commit-author.md:21
- Problem: GitHub derives `author.login` from the email in the commit. Anyone who sets `user.email` to the machine account's noreply address gets commits attributed to that account. The doc's claim that copying an address doesn't pass is the opposite of what happens. The check also ignores the committer and who pushed.
- Worst case: "The history tells you which agent did what" isn't guaranteed, and a fix for F01 that relies on commit authors would be bypassed the same way.
- Suggested fix: Require signatures: check `commit.verification.verified` and the signer, or turn on Require signed commits in the ruleset; reword the doc to say the check confirms only the email mapping.

## F13: Two checks pass silently when `MACHINE_ACCOUNT` is unset

- Severity: Medium. Category: CI gates. Evidence: code read.
- Where: files/commit-author/commit-author.yml:46-54; files/progress-file/progress-file.yml:43-47; guardrails/machine-account.md:37
- Problem: The ticket checks fail when the variable is empty, but `commit-author` skips its check step and succeeds, and `progress-file` prints "Opened by a person" and succeeds. The docs say they fail closed.
- Worst case: If the variable is deleted or renamed by mistake, both required checks stay green while checking nothing.
- Suggested fix: Add the same empty-value guard to both workflows and exit non-zero.

## F14: The PR's own code produces the JUnit results, and test config isn't read-only

- Severity: Medium. Category: CI gates. Evidence: code read.
- Where: files/no-weakened-tests/no-weakened-tests.yml:137-152; done-when.yml:119-133; check_read_only.py:32-36
- Problem: `conftest.py`, `pytest.ini`, `pyproject.toml`, the jest config, `package.json` scripts and the `Makefile` usually fall inside a ticket's scope and are not in `READ_ONLY_PATHS`. A pytest hook that reports failures as passes changes no test ID, so `no-weakened-tests` and `done-when` both pass. The docs admit only that a loosened assertion goes unnoticed.
- Worst case: Both CI test gates fail together, leaving the verifier's mutation spot-check, which is prose.
- Suggested fix: Add test configuration files to the default read-only list (changeable only when the ticket names the exact file); run the head's tests with the base's configuration; add sanity checks (the head has no fewer tests than the base, and a non-zero run time).

## F15: A verifier that pushes screenshots voids its own PASS

- Severity: Medium. Category: Skill logic contradictions. Evidence: code read.
- Where: skills/verify/SKILL.md:33; concepts/access.md:29; check_verdict.py:71-79
- Problem: The verifier may push screenshots to `docs/evidence/<ticket>/verify/` on the PR branch. A push moves the head, and a verdict is tied to a head commit: the PASS is void at once, `verdict` turns red, autopilot starts another verifier, and so on. That commit may also be outside the ticket's scope, and it puts the judge's changes on the branch being judged.
- Worst case: A ticket with a UI can't converge at Level 3 and keeps spending verifier sessions until the budget runs out.
- Suggested fix: The verifier doesn't write to the PR branch: evidence goes in comment attachments, a workflow artifact or a separate `evidence/<PR>` branch. To keep the current way, `check_verdict.py` must accept commits after a PASS that only add files under `docs/evidence/**/verify/`.

## F16: Fix rounds are defined three ways, and red-CI retries aren't counted

- Severity: Medium. Category: Skill logic contradictions. Evidence: code read.
- Where: skills/verify/SKILL.md:16,45; skills/autopilot/SKILL.md:26; tick.md:14; skills/build/SKILL.md:38-40; verify/verdict-template.md:6-7
- Problem: `build` and `escalation.md`: round 1 is fixed in the builder's own session. `autopilot`: every FAIL starts a fresh session (it is stateless and can't reach the original one). `verify`: the round is the verdict's ordinal, and it recommends escalating on a FAIL in round 2, which allows one fix, not the two that `Fix rounds: 2` promises. A red CI also starts a new build session, but only FAIL verdicts are counted.
- Worst case: When work escalates depends on which file the agent read; with a persistently red CI, builder sessions restart without limit except the 8-hour budget (see F17 for the budget).
- Suggested fix: Define it once, as a table in `states.md`: the round is the number of FAIL verdicts on the PR; FAIL number N+1 escalates. Drop the "same session" wording for autopilot. Count red-CI retries in a comment on the tracking issue and cap them.

## F17: Autopilot's claims, de-duplication and budget have no reliable state

- Severity: Medium. Category: Skill logic contradictions. Evidence: code read.
- Where: skills/autopilot/tick.md:25; wake.md:9,12; skills/autopilot/SKILL.md:37
- Problem: A claim is a remote branch with no expiry; when a builder dies, its ticket stays claimed for good, and agents are forbidden to delete remote branches. The de-duplication rule skips a PR whose latest autopilot comment is under ten minutes old, but autopilot posts each tick on the tracking issue, not on PRs. The budget is "5 tickets or 8 hours per run", yet a scheduled wake-up is a fresh session and so a new run, and nothing stores the start time.
- Worst case: A stuck ticket needs the Owner to delete a branch by hand; two ticks start a verifier or a fix session on the same PR and collide on non-fast-forward pushes; the budget is in effect unlimited.
- Suggested fix: Keep one status comment on the tracking issue that autopilot updates: the run's start time, the merged count, and each ticket's claim holder and expiry. An expired claim can be taken over. Use a GitHub Action `concurrency` group or an issue label as the tick's lock.

## F18: Two definitions of a done milestone, and the gap makes autopilot close it twice

- Severity: Medium. Category: Skill logic contradictions. Evidence: code read.
- Where: skills/report/SKILL.md:14; skills/plan/milestones.md:18,37-40; skills/autopilot/SKILL.md:15,36,44
- Problem: `report` says the sign-off is the Owner merging the plan PR that sets Status to done; `milestones.md` and `states.md` say it is merging the milestone PR, with `Status: done` set later by the next milestone's plan PR. Between those two merges, M<n> on `main` is still `active` with every ticket done: a stateless autopilot that wakes then matches "every ticket is done" and writes the report and opens the milestone PR again. The last milestone never becomes done.
- Worst case: Duplicate report sessions and empty milestone PRs; `/help` shows the wrong state.
- Suggested fix: Keep one definition: the milestone PR itself changes `Status` to `done` (a one-line exception like the ticket's). Autopilot's stop condition first checks for an already merged milestone PR.

## F19: "A user-invoked skill never calls another" contradicts how autopilot works

- Severity: Medium. Category: Skill logic contradictions. Evidence: partly unverified.
- Where: skills/README.md:12; skills/autopilot/SKILL.md:26-29,36,44; tick.md:21
- Problem: `build`, `verify`, `plan`, `design` and `report` all set `disable-model-invocation: true`, and autopilot's whole job is to start `/pitaya:build`, `/pitaya:verify` and the rest. That works for a new session given the slash command as its prompt; but `tick.md` allows falling back to a background agent or a subagent, where the model can't invoke a skill that has model invocation disabled (client-dependent, not tested).
- Worst case: Where only subagents are available, every autopilot tick does nothing, or the subagent works from memory without the skill's text.
- Suggested fix: Make the rule match the design: a coordinator starts other skills only through a new session with the slash command; for the subagent path, pass the skill file's path for it to read, as `verify` already does.

## F20: The verdict workflow has no concurrency control, and the status belongs to a commit, not a PR

- Severity: Medium. Category: CI gates. Evidence: code read.
- Where: files/agent-merge/agent-merge.yml:27-55
- Problem: Each run takes its own snapshot of the comments and then writes the status. When a PASS and a FAIL arrive close together, the run that started earlier and finished later writes `success` after the FAIL. A commit status belongs to a SHA: the same commit in another PR (or as the milestone branch's head after a fast-forward or rebase merge) carries `verdict: success` along.
- Worst case: A briefly wrong green is enough for an event-driven autopilot to merge.
- Suggested fix: Add `concurrency: { group: verdict-<PR>, cancel-in-progress: false }`; put the base branch in the context name, or check the PR's base in the script. Have autopilot re-read the verdict comments before merging (tick.md already asks it to re-read the head; add the FAIL check).

## F21: The control-plane inventory is incomplete
