# Decisions

The Owner's decisions. Append only: add a new row, never edit or delete an old one. To change a decision, add a row that supersedes it and name the old number.

D1 to D32 were made while designing pitaya and are listed in `docs/design.md`, section 11. New decisions start at D33 here.

| # | Date | Decision | Why | Supersedes |
| --- | --- | --- | --- | --- |
| D33 | 2026-11-19 | Every part of the harness is a component in `plugin/docs/components.json` with a level, `requires`, `recommends` and `needs`. Levels 0-3 are presets (every component up to that level); users may add or remove single components. `select_components.py` resolves a selection and only prints a plan; `levels.md` is generated from the manifest; tests derive dependencies from the recipes' own files and fail when the manifest declares fewer | Levels and their parts were spread over several docs, and dependencies (for example that every ticket check needs `MACHINE_ACCOUNT`) were only implied. One checked source lets a project pick its own set without missing a prerequisite, while adding a guardrail stays rule work | - |
| D34 | 2026-11-19 | `retro` and `handoff` belong to Level 1, not Level 3 | `retro` keeps the Level 1 memory files current (`learnings.md` above all) and `handoff` only needs a pushed branch; both pay off from the first project, not only for long-running autonomy | - |
| D35 | 2026-11-19 | Tickets have three modes: `docs/tickets/T-<nnn>.md` files mirrored by GitHub issues (recommended), files only, or issues only. In file modes the file is the source of truth and carries `Status: open`; the ticket's own PR sets it to `done` (with `Closes #<n>` for the mirror), and the scope and read-only checks allow exactly that line. `docs/tickets/**` is read-only by default. pitaya targets GitHub users only for now | Issue-only tickets can be edited by anyone with write access and have no status in files; a file read from the base branch can't be widened by its own PR, and the mirror keeps GitHub's discussion and notifications. Other hosts are deferred | - |
| D36 | 2026-11-20 | File tickets reach `main` through a plan PR on a `plan/<slug>` branch. The shared "Find the ticket" step skips ticket checks for it and fails it if it changes anything but `docs/tickets/*.md`, the glossary, the architecture map and `docs/decisions.md` | Without it, a machine-account plan PR failed every Level 2 ticket check (no ticket branch), so file tickets couldn't be planned once Level 2 was on; the path limit keeps the branch name from being a way around the checks | - |
| D37 | 2026-11-20 | "Only the Owner merges" is enforced, not just written: protect-main requires 1 approval (dismissed on new pushes) and a new Level 1 hook, `ask_on_merge.py`, asks before `gh pr merge`, the merge API or the GitHub merge tool unless the harness file's Autonomy line lets agents merge. With agent-merge, approvals drop to 0 and the `verdict` status takes their place | With 0 required approvals, a machine account with Write access could merge any green PR, so Levels 1-2 relied on prose | - |
| D38 | 2026-11-20 | Planning has two levels: `/plan --roadmap` writes `docs/milestones/M<n>.md` (goal, demoable exit criteria, what's left out, Status planned/active/done), and `/plan M<n>` cuts the active milestone into tickets only when it starts. No milestone branches: tickets merge into `main`; `/report M<n>` checks the exit criteria and the Owner's merge of a plan PR that sets `Status: done` is the sign-off. `docs/milestones/**` is read-only for ticket PRs; plan PRs may change it. The roadmap is made by `/plan` right after `/setup`, not inside it | Tickets alone gave no larger goal or sign-off point, and `/autopilot` needs a bounded unit to run; cutting tickets just in time keeps later milestones open to what earlier ones teach; no long-lived branches | - |
| D39 | 2026-11-20 | A Level 3 `/autopilot` skill runs one active milestone. Each tick is stateless (rebuilt from `main`, PRs, verdicts and a tracking issue), hands every build, verify and report to a fresh session or agent, merges only when the Autonomy line allows and no sensitive area is touched, and stops at Owner gates: plan PRs, sensitive areas, fix rounds, milestone sign-off, a budget (default 5 tickets or 8 hours) and an Owner "stop". pitaya ships no scheduler; ticks are woken by PR events, `/loop`, a schedule or a GitHub Action. R3 is refined: an orchestrator never runs another in its own context, but `/autopilot` may start one in a fresh session | The Owner wants Level 3 automated without giving up plan approval and sign-off; unlike pstack's autopilot it keeps human gates and a budget. Stateless ticks survive a lost session, and dispatching to fresh sessions keeps the coordinator's context small | - |
| D40 | 2026-11-20 | Audit batch A. `ask_on_merge.py` reads only the Autonomy field's value (the template's note no longer turns it off); all Bash hooks look inside `sh -c` and `eval`, `ask_on_merge.py` also after gh's `-R` and at the GraphQL merge and auto-merge mutations and auto-merge tools; `no_push_main.py` handles `--repo`; rule files are all of `.github/`, and inline `python -c`/`node -e` code naming a rule file asks; workflow step outputs reach scripts only through `env:`; the Read tool is also denied nested `.env` files. D37's "enforced" is clarified: hooks are early warnings that a determined script can get around; the guarantee is the ruleset's approval, which batch C ties to a code owner | An independent audit found the merge hook silent with the shipped template, several hook bypasses, check scripts outside the rule-file hook, a branch-name injection path and an overstated secrets claim | D37 (wording) |
