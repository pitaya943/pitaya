# W8 trial record

The W8 trial runs pitaya on a new repository from Level 0 up, one milestone per level, in Claude Code cloud sessions whose environment installs the plugin (D54). This file records what happened, with links to the evidence, and what it means for pitaya. Each part is added when its milestone ends.

- Trial repository: `<owner>/pitaya-trial`, seeded with `tally` (a Python library and CLI that splits shared expenses; 21 tests).
- Environment: a personal cloud environment whose setup script runs `claude plugin marketplace add` and `claude plugin install pitaya@pitaya`, then builds the project's virtualenv.
- Plugin version: 0.1.1.

### What worked

1. **The verifier found real gaps the builder's tests missed, twice.** Round 1: a mutation at the 12/13 cap (`<= EXACT_LIMIT + 1`) survived all 880 tests. Round 2: removing `settle_up`'s greedy dispatch survived all 884, because the tests compared against inputs where both methods give the same answer. Both times the product was right and the tests were not; the mutation spot-check (checklist item 5) and "tests are real" (item 4) caught it. Evidence: the round 1 and round 2 verdicts on PR #8.
2. **Escalation worked as designed.** After the last fix round, the agent stopped, opened a `needs-owner` issue with three options, consequences and a recommendation, and the Owner chose one. The extra round, the corrected example and the closing decision were each recorded (D-6 to D-8). Evidence: issue #9, PR #10.
3. **The builder caught a wrong spec example.** T-002 condition 2's example ({+5, −5, +3, −3}) gives 2 payments with greedy in every order, so it couldn't show the exact method beating greedy. The builder replaced it with one that does (exact 3, greedy 4), the Owner approved, and D-6 records it. Evidence: PR #8 hand-off, D-6.
4. **Decisions and ADRs came out at the right grain.** Two ADRs for choices with real options (the settle-up algorithm, rounding for proportional splits); one-row decisions for the rest.
5. **The report checked every exit criterion with a command**, said where a check differed from the criterion, and listed what isn't done.

### Other observations

- **Rule changes always need the Owner's bypass.** Any PR from the machine account that isn't on a ticket branch (PRs #13, #14) fails the ticket checks by design. That's intended (rule work is the Owner's, or a ticket that names the exact files), but the guide should say so before the first one.
- **The model line differs between sessions.** Part 1's verifiers wrote "withheld" (P2), while the T-003 builder named the model. Both are allowed; it shows the environment's instruction isn't applied the same way in every session.
- **The Owner's personal Claude preferences reach the trial sessions.** The verifier sessions answered in two languages and asked the Owner to pick a session mode, because account-level preferences apply to every session. pitaya's skills didn't ask for either; the trial's agents behave slightly differently from a plain user's.
- **Product questions the builders raised, for the Owner, not pitaya:** new ledger files are created with mode 0600 (from `mkstemp`) instead of 0644; the directory isn't `fsync`ed after the rename; a ledger whose top level isn't a JSON object still raises a raw exception.
