# W8 trial record

The W8 trial runs pitaya on a new repository from Level 0 up, one milestone per level, in Claude Code cloud sessions whose environment installs the plugin (D54). This file records what happened, with links to the evidence, and what it means for pitaya. Each part is added when its milestone ends.

- Trial repository: `<owner>/pitaya-trial`, seeded with `tally` (a Python library and CLI that splits shared expenses; 21 tests).
- Environment: a personal cloud environment whose setup script runs `claude plugin marketplace add` and `claude plugin install pitaya@pitaya`, then builds the project's virtualenv.
- Plugin version: 0.1.1.

Tests went from 21 to 885 (each seeded property case is its own test ID). The exact method takes 0.004 s at its 12-member limit.

### What worked

1. **The verifier found real gaps the builder's tests missed, twice.** Round 1: a mutation at the 12/13 cap (`<= EXACT_LIMIT + 1`) survived all 880 tests. Round 2: removing `settle_up`'s greedy dispatch survived all 884, because the tests compared against inputs where both methods give the same answer. Both times the product was right and the tests were not; the mutation spot-check (checklist item 5) and "tests are real" (item 4) caught it. Evidence: the round 1 and round 2 verdicts on PR #8.
2. **Escalation worked as designed.** After the last fix round, the agent stopped, opened a `needs-owner` issue with three options, consequences and a recommendation, and the Owner chose one. The extra round, the corrected example and the closing decision were each recorded (D-6 to D-8). Evidence: issue #9, PR #10.
3. **The builder caught a wrong spec example.** T-002 condition 2's example ({+5, −5, +3, −3}) gives 2 payments with greedy in every order, so it couldn't show the exact method beating greedy. The builder replaced it with one that does (exact 3, greedy 4), the Owner approved, and D-6 records it. Evidence: PR #8 hand-off, D-6.
4. **Decisions and ADRs came out at the right grain.** Two ADRs for choices with real options (the settle-up algorithm, rounding for proportional splits); one-row decisions for the rest.
5. **The report checked every exit criterion with a command**, said where a check differed from the criterion, and listed what isn't done.

### Problems found in pitaya

| # | Problem | Impact | Proposed fix |
| --- | --- | --- | --- |
| P1 | **Every PR came from the cloud session's assigned branch** (`claude/<session-name>`), not `plan/<slug>` or `ticket/<id>-<slug>`. A cloud session only pushes to its assigned branch unless the user allows another | Level 1 doesn't check branch names, so nothing broke. At Level 2 the ticket checks find the ticket by branch name, so every PR would fail; at Level 3 `/autopilot` claims tickets by branch | `/build` and `/plan` say which branch name they need, and that in a cloud session the user grants it; the README's cloud section says to grant it when starting a session. Until then, the user grants it in the session's first message |
| P2 | **The verdict can't name the model in a cloud session.** The environment forbids model identifiers in repository text, so every verdict said "withheld from repository text by this environment's policy" | pitaya requires the model's name (the `evidence` skill); its only fallback is "unavailable", which isn't what happened | The `evidence` skill accepts "withheld" with the reason, and says the model then goes to the Owner in the session |
| P3 | **A wrong worked example reached a ticket.** `/plan` wrote an example that couldn't satisfy its own condition | One fix and a decision row; caught only because the builder checked | `/plan`'s ticket step: run or compute every worked example before writing it into a condition |
| P4 | **"One more fix round" has no rule.** The Owner authorised a third round; nothing in pitaya describes it | It worked, but each project will improvise it | `concepts/escalation.md`: the Owner may authorise extra rounds through the escalation issue; the verdict says which round and links the authorisation |
| P5 | **The issue mirror can't get GitHub milestones.** `plan/milestones.md` asks for one GitHub milestone per milestone file, and the session's GitHub tools can't create milestones | The mirror issues have no milestone; the report says so | `plan/milestones.md`: create them when the tools can, otherwise say so in the plan PR |
| P6 | **The PR's "How to verify" went stale after fix rounds** (`880 passed` while the head had 885) | The verifier flagged it as a minor gap | `/build`: update "How to verify" and "Scope" in each fix round |

| P7 | **M1 had no milestone branch; every ticket merged straight into `main`.** `concepts/states.md` said milestone branches start at Level 3, contradicting D44, and nothing created the branch after the Owner merged the cut, so `/build` silently fell back to `main` | `main` held half a milestone after T-001, and M1 couldn't have been thrown away as a whole; at Level 3 the milestone branch is the only bound on what agents merge | Milestone branches at every level (D56): `/build` creates a missing one instead of using `main`, `/help` reports it, `states.md` is corrected |

All seven are fixed in 0.1.2 (D55, D56).

### Learnings proposed for the project (not for pitaya)

The verifiers proposed, and the retro carries in PR #12: to pin "path X is used above a threshold", test at exactly the threshold with an input where the two paths give observably different results, and assert where the decision is made.
